# Notion制作物の読み取り・ダブルチェック・続き生成 設計

- **日付**: 2026-07-16
- **対象システム**: CUBOCCI STUDIO AI組織（runner.py 週次エージェント ＋ Claude Code サブエージェント）
- **ステータス**: 設計合意済み → 実装計画へ

## 背景・課題

現状、Notion連携は **書き込み専用（一方通行）** である。

- `tools.py:save_to_notion()` はページを作成し本文ブロックを追記するだけで、読み取り機能がない。
- 保存は `app.py` / `runner.py` 側でエージェントの作業完了後に自動実行され、エージェント自身の `TOOL_DEFINITIONS`（`web_search` / `search_papers` / `fetch_page`）には含まれない。
- したがってエージェントは、過去の制作物も生成途中の成果物も一切参照できない。

さらに **品質バグ** が発覚した。runner.py の生成ループ（`run_agent`）は `stop_reason` を分岐せず、ツール使用以外の終了理由をすべて「完成」として保存する（`runner.py:89` の `else` 分岐）。`max_tokens`（現状 16000）に達して途中切れした文章も「完了✅」としてNotionに保存されてしまう。オーナーが「完成なのに文章が途中で切れている」制作物を発見した原因はこれ。

## ゴール

1. 週次Pythonエージェントと Claude Code サブエージェントの双方が、Notionの既存制作物を **読める** ようにする。
2. 「途中／要確認／完成」の状態を見分け、**途中のものは続きを生成** できるようにする。
3. エージェントが「完成」と誤判定した途中切れを防ぎ、**オーナーの最終チェック（ダブルチェック）** を経て初めて「完成」とする体制を作る。
4. **これまでの制作物** も対象に含める（途中切れの自動仕分け＋再開）。

## スコープ

対象は3ケースすべて（混在）:
- 週次パイプラインの工程間の引き継ぎ（月テーマ→火台本→…）
- エラー・API制限で中断したもの
- 意図的な下書き

## アーキテクチャ方針

**A案（採用）**: 既存の `save_to_notion`（書き込み）と対になる **Python製の軽量Notion読み取り/更新関数** を `tools.py` に追加し、`TOOL_DEFINITIONS` に登録する。runner.py のツールループでそのまま使え、Claude Code 側もこの関数群を共有できる。

- B案（runner.py を Notion公式MCPサーバーに載せ替え）は不採用。MCPクライアント基盤の新規構築が必要で今回の目的にはオーバースペック。
- Claude Code の私・`@sommelier` 等のサブエージェントは、既存の `mcp__claude_ai_Notion__*` でも読めるが、統一のため本設計の関数群も利用可能とする。

## 詳細設計

### 1. Notionステータス（データモデル）

「コンテンツ生成物」DB（`NOTION_DATABASE_ID`）に **セレクト型プロパティ `ステータス`** を追加する（`カテゴリ` の隣）。

| ステータス | 意味 | 誰がセット |
|---|---|---|
| `途中` | 生成の途中切れ／中断／意図的下書き。**次回エージェントが続きを作る対象** | エージェント（自動）＋オーナー（差し戻し時） |
| `要確認` | エージェントは完成したつもり。**オーナーのダブルチェック待ち** | エージェント（自動） |
| `完成` | オーナーがチェックしOKを出した最終版 | オーナー（Notion上で手動） |

- プロパティ追加は Notion API/MCP で自動実行してよい（オーナー承認済み）。
- 運用フロー: オーナーは Notion で `ステータス = 要確認` を絞り込み → 読む → OKなら `完成`、不十分なら `途中` に戻す。`途中` に戻したものは次回自動で続きが作られる。

### 2. 途中切れの検知＆自動継続（runner.py）

`run_agent` の生成ループを `stop_reason` で分岐させる。

- `stop_reason == "max_tokens"`（上限で途中切れ）→ **(a) 自動継続を採用**: `messages` に続きを促して生成ループを継続し、結合した全文を保存する。`max_tokens` 上限も 32000 程度に引き上げる。それでもなお切れる場合は `途中` ステータスにフォールバックし次回に回す。
- `stop_reason == "end_turn"`（正常終了）→ これまで通り保存し、ステータス `要確認` で登録。

これにより「切れたまま完成」は原理的に発生しない。

### 3. Notion読み取り/更新ツール（tools.py + TOOL_DEFINITIONS）

`save_to_notion` と対になる関数を追加し `TOOL_DEFINITIONS` に登録する。

| ツール | 役割 | 主なパラメータ |
|---|---|---|
| `notion_find_wip` | `ステータス=途中` のページ一覧（id・タイトル・カテゴリ） | `category?`（ワイン/コーヒー等で絞り込み） |
| `notion_read_page` | 指定ページの本文テキストを取得 | `page_id` |
| `notion_update_status` | ステータスを更新（続き完成時に `要確認` へ 等） | `page_id`, `status` |

- Notion API 呼び出しは既存 `save_to_notion` と同じ `Notion-Version: 2022-06-28` / Bearer トークン方式を踏襲。
- 環境変数未設定時は `save_to_notion` 同様スキップメッセージを返し、既存動作を壊さない。

### 4. 続きを作るフロー（エージェント動作）

週次エージェント（例: 火曜の台本作成）の冒頭で:
1. `notion_find_wip(category)` を呼ぶ。
2. 同カテゴリに `途中` があれば `notion_read_page` で本文を読み込み、**続きから執筆**。
3. 完成したら元ページを更新（追記）しつつ `notion_update_status(page_id, "要確認")`。
4. `途中` が無ければ通常どおり新規作成し、`要確認` で保存。

過去の制作物には元の指示プロンプトが残らないため、エージェントは **タイトル＋既存本文から意図を汲んで** 続きを書く（実用上十分、100%元意図一致は保証しない旨を明記）。

### 5. これまでの制作物への対応（後方互換・自動仕分け）

`ステータス` プロパティ追加時、既存ページの本文を機械的にチェックして初期値を仕分ける:
- **途中切れらしいもの**（文が途中で終わる／不自然に短い／締めの段落が無い）→ `途中`
- **それ以外** → `要確認`

`途中` になった過去分は、週次エージェント（同カテゴリ）または Claude Code 手動指定（任意ページ）で再開できる。

### 6. 途中切れ判定ロジック（純粋関数）

検知は副作用のない純粋関数として切り出し、単体テスト可能にする。入力: 本文テキスト。出力: `途中` / `要確認`。判定シグナル（例）:
- 末尾が文の途中（句点・閉じ括弧・締めの記号で終わっていない）
- 極端に短い（しきい値未満）
- 想定される締めの段落・ハッシュタグ等が欠落

runner.py 側は `stop_reason == "max_tokens"` を一次シグナルとし、過去分の後方仕分けはこの純粋関数を使う。

## テスト設計

既存構成（`tests/`・`conftest.py`・`pytest`）に合わせ、Notion API は **モック化**して検証する。

- **読み取り/更新ツール**: `notion_find_wip` / `notion_read_page` / `notion_update_status` が、モックAPIレスポンスを正しくパース・整形・送信するか。
- **途中切れ検知ロジック**: 本文サンプル（正常な締め／文中でブツ切れ／極端に短い）で `途中` / `要確認` 判定が正しいか。
- **runner.py 継続ループ**: `stop_reason="max_tokens"` を返すモッククライアントで、自動継続 → 全文結合 → 保存 の流れが動くか。
- **後方互換**: `ステータス` 未設定の既存ページでも `save_to_notion` が壊れないか。

## 影響範囲

- `tools.py`: 読み取り/更新関数3つ・途中切れ判定関数・`TOOL_DEFINITIONS` 追記・`save_to_notion` にステータス付与。
- `runner.py`: `run_agent` の `stop_reason` 分岐、`max_tokens` 引き上げ、続き生成フロー。
- `tests/`: 新規テスト追加。
- Notion「コンテンツ生成物」DB: `ステータス` プロパティ追加＋既存ページの初期仕分け（1回のマイグレーション操作）。
- `app.py`: 手動モードでも同様の保存経路を通るため、必要に応じてステータス付与を反映。

## 非対象（YAGNI）

- runner.py の MCP 化（B案）。
- Notion 以外の保存先（note記事の下書き等）への状態管理拡張。
- 通知UIの新設（オーナーは Notion のビュー絞り込みでチェックするため不要）。
